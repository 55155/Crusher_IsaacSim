# Real2Sim — Crusher 반력 프로파일 준정적 재현

실기 Crusher(크랭크-슬라이더 정제 분쇄기)에서 ForceGage로 측정한 **크랭크 각도별
반력**을 시뮬레이션에서 물리적으로 재현하고, 준정적 실험값에 피팅하기까지 사용한
테크닉·시행착오를 정리한다.

- 실기 제어 알고리즘: [`TabletCrusher/Motor/Keyborad_control_v3.py`](../TabletCrusher/Motor/Keyborad_control_v3.py) (v3 FSM)
- 최종 시뮬: [`Crusher_Genesis/Crusher_8env.py`](../Crusher_Genesis/Crusher_8env.py) (MuJoCo, 8-env 병렬)
- 기구·사양: [`Crusher.md`](Crusher.md), [`motor_spec.md`](motor_spec.md)

---

## 1. 목표와 물리적 대전제

**목표**: v3 알고리즘(STRIKE/RETRACT FSM)으로 구동한 실기의 반력 `F(θ)`를 시뮬이
재현. 크랭크 각도 θ = 15·30·45·60·75·90·105·120°에서 측정한 8개 프로파일(각 ~10분)에
정합.

**대전제 — 반력은 지령값이 아니라 창발값**:
크랭크-슬라이더에서 슬라이더 반력은
```
F_slider = τ_crank / (r · sinθ)
```
즉 (크랭크 각도) × (저항)의 결과로 *창발*한다. 직접 "600 N 내라"고 명령하는 값이
아니다. → 시뮬에서도 힘을 **주입하면 비물리적**이고, 기구가 벽을 눌러 **접촉에서
창발**해야 한다. 이 원칙이 전체 설계를 지배했다.

## 2. 측정 데이터 파이프라인 (Real 쪽)

| 단계 | 내용 |
|------|------|
| 원본 | ForceGage 텍스트/`.xls`(`NO.\|Time\|Value(N)\|Pressure`) + v3 RPM 로그 CSV(`elapsed_s,rpm,state,crank_deg`) |
| 파일명 복구 | 깨진 한글 파일명 → 선두 숫자(=크랭크 degree) 기반 `{θ}deg.txt` 재명명 |
| 시간축 재구성 | 시계값(1초 해상도) → 고정 샘플레이트(≈5.3 Hz)로 Real time[s] 복원, 10분 crop |
| **이상치 처리** | 스트라이크별 피크 검출 → **median 기반**(median±3.5·MAD) 이상치를 **median으로 대체**(평균 아님). 대표값 = 이상치 제거 후 **mean(clean)** |
| **RPM–Force 동기화** | 시작 시각 상이 → **접촉 이벤트 상호상관**(힘=피크, RPM=급락) 으로 오프셋(−4~−9s) 추정 후 정렬 |

로버스트 대표 반력(측정): θ=30→896, 45→596, 60→515, 75→456, 90→503, 105→394, 120→563 N.
F–θ는 U자형으로 나와 기구 이득식과 일치하되, **최소는 90°가 아니라 75°(456 N)** 다.
근사식 `F = τ/(r·sinθ)` 는 90°에서 최소지만, 이 기구는 r/L = 20/80 = **0.25** 라
로드 기울기를 뺄 수 없다 — 정확한 기구 이득 `|dx/dθ| = r·sinθ·(1+λcosθ/√(1−λ²sin²θ))`
는 λ=0.25 에서 최대(= F 최소)가 **θ ≈ 77°** 로 옮겨가 측정 최소점 75° 와 맞는다.
(다만 이 보정을 §2-1 역산에 그대로 넣으면 토크 산포는 CV 6.2% → 7.5% 로 오히려
악화한다 — 최소점 *위치*만 설명되고 *크기*는 아직 안 맞는다.)
60° vs 120°(같은 sinθ)의 차이는 **CW/CCW 토크 비대칭**([`Crusher.md`](Crusher.md)
§12-8)의 실측 증거.

### 2-1. 역산 검산 — 반력을 토크로 되돌리면 한 점으로 모인다

§1 의 대전제 `F = τ/(r·sinθ)` 를 뒤집어 `τ = F·r·sinθ` 로 측정 반력에서 크랭크
토크를 역산한 것. **모터 토크는 실측한 적이 없다** — 실기 로그는 RPM 뿐이고
([`Motor/rpm_log_*.csv`](../TabletCrusher/Motor/)), [`motor_spec.md`](motor_spec.md) §3 의
`τ_crank = 12.5 N·m` 자체가 "실측 역산: F_slider × r" 이다. 따라서 아래는 독립
측정 둘의 상관이 아니라 **항등식의 자기일관성 검산**이다.

| θ [°] | 30 | 45 | 60 | 75 | 90 | 105 | 120 |
|---|---|---|---|---|---|---|---|
| F 실측 [N] | 896 | 596 | 515 | 456 | 503 | *394* | 563 |
| 역산 τ [N·m] | 8.96 | 8.43 | 8.92 | 8.81 | 10.06 | *7.61* | 9.75 |

**105° 제외 평균 9.16 N·m, CV 6.2%.** 반력은 456~896 N 으로 2배 흔들리는데 토크는
8.4~10.1 N·m 한 점으로 모인다 — 반력의 각도 의존성이 전부 기구 이득 `1/sinθ` 로
설명되고 모터는 각도와 무관한 stall 토크를 낸다는 뜻. **준정적 가정이 실측에서
성립한다는 증거**다.

남는 잔차 셋:

- **105° = 7.61 N·m** — 인접 각도 대비 −17%. `Crusher_8env` 의 `MEASURED`·`FORCE_SCALE`
  재적합에서 제외한 이상치([`DigitalTwin.md`](DigitalTwin.md) §6-7).
- **60°(8.92) vs 120°(9.75)** — sinθ 가 같은데 +9%. 링크 자중은 두 자세에서 부호가
  반대고 슬라이더 측력 마찰(`μ·tanφ`)은 두 각도에서 값이 같으므로, 둘 다 이 차이를
  못 만든다. 남는 설명은 감속기 방향별 효율([`Crusher.md`](Crusher.md) §12-8) 뿐.
- **9.16 vs 12.5** — [`motor_spec.md`](motor_spec.md) 의 12.5 는 초기 실측 "90°에서
  600–650 N"(625×0.02)에서 왔는데, ForceGage 캠페인의 90° robust-mean 은 503 N →
  10.06 N·m 이다. 두 실측 세트가 ~25% 어긋나 있고, 감속기 전달효율도 32%(12.5 기준)
  vs 23%(9.16 기준)로 갈린다. **미해결.**

## 3. 시뮬 접근의 진화 — playback → 물리 창발

1. **개루프 playback (기각)**: 측정 `F(θ)`를 벽 링크에 외력으로 인가.
   → *무조건 일치*하지만 힘을 억지로 부여하는 **비물리적** 방식이라 폐기.
2. **감속기 역할 모델링**: 실기가 준정적인 이유는 수동적 결과가 아니라
   **감속기 + 속도서보** 때문임을 반영.
3. **물리 창발**: 크랭크토크 → 기구 → 벽 접촉에서 반력이 *창발*. 측정과의 정합은
   힘 주입이 아니라 **스칼라 캘리브 + 위상 보정**으로 달성.

## 4. Genesis에서의 구현 어려움 (왜 못 썼나)

처음엔 Genesis(`gs.cuda`, RTX 5080)로 시도했으나 **폐루프(closed-loop) weld가
결정성을 못 줬다.**

| 문제 | 증상 | 원인 |
|------|------|------|
| **폐루프 비결정성** | 동일 크랭크각인데 슬라이더 Y가 실행마다 **17 mm 차이**(0.2355 vs 0.2183) | weld equality가 크랭크–로드–슬라이더 폐루프에서 config를 유일하게 못 품 |
| stiff/dt 무효 | weld timeconst 1 ms + dt=0.0005로 강성을 올려도 비결정성 유지 | 강성/스텝 문제가 아니라 솔버가 폐루프를 branch |
| 속도 | dt=0.0005 stiff → GPU 단일 289 steps/s (오히려 느림) | 무거운 제약 |
| 부수효과 | armature 없으면 velocity actuator 발산(관성 4e-5, kv 14.9) | 반영관성 미주입 |

**결론**: Genesis는 이 닫힌 기구 루프에 부적합. 원본 sim 엔진인 **MuJoCo로 전환**.
(MuJoCo는 `crank_slider_loop` weld를 결정적으로 처리하도록 설계됨 — [`Crusher.md`](Crusher.md) §6.)

## 5. 핵심 테크닉 (MuJoCo 최종안)

### 5-1. 감속기 반영관성 = `armature`
감속기의 물리적 3효과(토크×N, 관성×N², 속도÷N) 중 **반영관성**을 크랭크 관절에
주입:
```python
model.dof_armature[crank_dof] = J_motor · N² = 72e-7 × 212² ≈ 0.324 kg·m²
```
이것이 **①준정적**(관성이 커 천천히·매끄럽게 반응)과 **②수치안정**(velocity
actuator 발산 방지)을 동시에 해결. 이게 빠진 채 구동하면 크랭크가 회전 못 하고
진동만 함(qvel은 튀는데 위치는 정지).

### 5-2. 준정적 = 속도서보(토크제어 아님)
순수 토크 FF로는 속도를 못 잡는다(α=τ/J, 작은 J → 폭주). 실기 BLDC 드라이버가
**속도서보**이므로 시뮬도 velocity actuator로 8 RPM 추종(`forcerange`=τ_stall).
준정적 정량: `Q = m·r·ω²/F ≈ 8.6×10⁻⁶ ≪ 1`. 속도 자체는 힘과 무관(준정적)이라,
느린 8 RPM 대신 큰 dt로 계산만 가속 가능(60 RPM 압축은 준정적 위배라 지양).

### 5-3. 힘의 창발 — 정제 대신 강체 벽
- 정제는 **두께 편차**로 접촉각이 불확정 → **강체 box 벽**을 정확한 위치에 배치
  (위치 결정적, 힘 센싱 가능).
- **plate–box 전용 충돌 그룹**(contype/conaffinity=4, 나머지 전부 0)으로 기구 다른
  부위와의 스퓨리어스 충돌 완전 차단.
- 힘은 크랭크가 플레이트를 밀어 벽에 접촉·stall하며 창발: `F ≈ τ_stall/(r·sinθ)`.

### 5-4. FSM 구동
[`Keyborad_control_v3.py`](../TabletCrusher/Motor/Keyborad_control_v3.py)와 동일: STRIKE(+, BDC→TDC 스윕)에서 벽 접촉 stall →
RETRACT(−, BDC 재장전) → 반복. lock_crank equality로 Phase 1 안정화 후 해제.

### 5-5. 접촉각 결정 & 위상 보정
- BDC(−178°)에서 STRIKE 시작해 θ180→0 전 구간을 쓸어 θ=15~120° 전부 커버.
- 벽을 `slider_Y(θ)`에 놓으면 실제 접촉이 **일관되게 목표+7.5°**에서 발생 →
  벽을 **(목표−7.5°)** 위치에 배치하는 **위상 보정**으로 접촉각 = 목표 정렬.

### 5-6. 캘리브레이션 & realism
- **힘 스칼라** `k≈0.98` (측정/sim 최소자승 = forcerange 12.3 등가).
- **노이즈**: 스트라이크간 피크 변동(~4% CV) + 가산 센서 노이즈(~4 N) → 실측처럼 보임.

### 5-7. 병렬 실행
각 각도(=1 env)가 독립 → `multiprocessing.Pool`로 **8 프로세스 병렬**.
전체 wall-time **≈5초** (실기 실험은 각도당 10분×8=80분).

## 7. 교훈 요약

1. **닫힌 기구 루프는 솔버를 탄다** — Genesis 폐루프 weld 비결정성. 도구 선택이 중요
   (이 문제엔 MuJoCo).
2. **감속기 = armature** — 반영관성 하나로 준정적 + 수치안정 동시 해결.
3. **준정적은 속도서보** — 토크제어 아님. 실기 드라이버를 그대로 모델링한 것.
4. **힘은 창발** — 주입 금지. 접촉에서 나오게 하고, 정합은 스칼라·위상으로.
5. **정제 대신 강체 벽** — 두께 편차 제거, 접촉각 결정성 확보.
6. **위상 보정** — 벽 배치각과 실제 접촉각의 일관된 오프셋을 상수로 보정.
